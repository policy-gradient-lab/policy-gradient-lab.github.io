Benchmarks that measure a language model’s single-turn capability, such as MMLU, GPQA, and HumanEval, have approached saturation at the frontier, while benchmarks that measure multi-step task completion, such as SWE-bench, WebArena, and OSWorld, retain large headroom (Guo et al. 2026). The two trends diverge: raising model capability yields diminishing returns on precisely the agentic tasks that the static benchmarks no longer discriminate. This is the framing the recent literature takes as organizing. If scaling the model alone does not close the gap on multi-step tasks, what does (Guo et al. 2026)?

One empirical answer predates that framing. SWE-agent held the base model fixed and changed only the interface through which the model reads and acts on a computer, and that change moved task performance substantially (Yang et al. 2024). The remaining gap is attributed not to the model but to the runtime around it. This post defines that runtime, the execution harness, and the responsibilities it carries.

1 An Agent Is a Model Plus a Harness

The harness-design survey writes an LLM-based agent not as a model but as a pair (Guo et al. 2026):

A = \langle \mathcal{M}, \mathcal{H} \rangle.

Here \mathcal{M} is the foundation model, which supplies the general cognitive capability that makes open-ended task completion possible, and \mathcal{H} is the execution harness, the runtime that mediates closed-loop interaction between the model and the external world.

Why write the agent this way rather than treating the harness as prompt scaffolding around a model? Because prompting is feedforward. It optimizes the input to each reasoning step but supplies no mechanism to detect drift, verify an intermediate outcome, or recover from an error (Guo et al. 2026). Folding the runtime into the prompt hides the components that do that work. The pair notation instead separates the part that provides capability from the part that determines whether capability becomes reliable completion, so that the two can be studied and optimized independently.

The term harness engineering was crystallized by Hashimoto and by OpenAI, who framed an agent as model plus harness and named observation shaping, action-space design, sandboxing, context management, and verification as its components, as the survey recounts (Guo et al. 2026).

2 Interface, Not Only Model, Moves Performance

SWE-agent introduced the agent-computer interface (ACI), an abstraction layer between the model and the computer that fixes the commands the agent can issue and the format of the feedback it receives (Yang et al. 2024). The design is drawn by analogy to human-computer interaction: a shell that serves a human user well is not the interface that serves a language model best.

With GPT-4 Turbo, SWE-agent resolves 12.47% of the 2294 SWE-bench test tasks, against a previous best of 3.8% from a non-interactive, retrieval-augmented system (Yang et al. 2024). That comparison changes both the system and the interaction mode, so the paper isolates the interface with an ablation on the 300-instance SWE-bench Lite subset: the same agent solves 10.7 percentage points more instances with the ACI than with only a default Linux shell. The ACI was tuned for GPT-4 Turbo but transfers, resolving 10.5% of tasks with Claude 3 Opus. The gain therefore attaches to the interface, holds across base models, and requires no change to model weights.

Why does interface design carry this weight? A Linux shell is configurable for a human but gives an agent no compact command to edit a small file span and returns no feedback when an edit is invalid (Yang et al. 2024). The agent’s effective ability is bounded by what its interface makes expressible and legible, not only by what the model could in principle do. Redesigning the interface changes both what the model observes and how it acts, which is why the same weights produce different task success under different ACIs.

3 Where the Bottleneck Sits

The survey organizes agent engineering into four paradigms, each foregrounding a different performance lever (Guo et al. 2026). Prompt engineering optimizes the single instruction sent to the model and addresses how a task is posed. Workflows and context engineering move the unit of optimization to the information lifecycle around multi-step execution, curating what enters the context window, when, and in what form. Harness engineering closes the loop: the model acts, observes the environment’s response, and reasons over that observation to choose the next step (Yao et al. 2023), and the runtime, not the prompt, governs whether execution stays on track. Agent-native training and co-evolution internalize agentic behavior into weights and, over deployment, update the model, harness, and improvement loop from execution traces.

The survey presents these as coexisting stages rather than replacements, and reads the history as a migration of the bottleneck from eliciting model behavior, to organizing context, to controlling execution, and toward learnable runtimes. The claim it draws from that reading is that agent performance is a property of the model-harness pairing, not of the model in isolation (Guo et al. 2026). This series takes the harness side of that pairing as its subject.

4 The Six Runtime Responsibilities of a Harness

Within the pairing, the survey decomposes the harness into six coupled components (Guo et al. 2026):

\mathcal{H} = \langle \mathcal{I}_{\mathrm{obs}}, \mathcal{C}, \mathcal{L}, \mathcal{I}_{\mathrm{act}}, \mathcal{S}, \mathcal{V} \rangle.

The observation interface \mathcal{I}_{\mathrm{obs}} determines which environment signals are exposed to the model and how they are rendered. The context manager \mathcal{C} selects, compresses, orders, and refreshes what actually enters the current model call. The control loop \mathcal{L} organizes execution across steps, tools, and handoffs, turning observation, reasoning, action, and feedback into a runnable process. The action interface \mathcal{I}_{\mathrm{act}} maps model outputs to executable operations and defines what the agent can do. The state and artifact store \mathcal{S} persists progress, traces, and artifacts beyond the active context window. The verification and governance layer \mathcal{V} checks, constrains, and repairs execution through tests, judges, sandboxing, budgets, and rollback.

Why decompose by runtime responsibility rather than by software module? The survey states that the decomposition is not a package diagram; each element names a recurring point at which model capability either does or does not become reliable completion (Guo et al. 2026). A long-horizon failure is often not a failure of reasoning but of legibility, of a missing action, or of an unverified step, and the six axes name where those failures occur.

Why treat the six as coupled rather than independent modules? Because a choice in one shifts burden onto another. Richer observations improve grounding but raise the cost the context manager must pay to select and compress them. More expressive actions widen capability but demand stronger verification and governance. Harness design is therefore a coupled systems problem, and the same six axes double as a way to read a task, since different domains, horizons, and oracle strengths stress different components. Concurrent 2026 surveys reach similar decompositions, one formalizing the harness as a six-component tuple and another as a seven-layer taxonomy, as this survey catalogs (Guo et al. 2026).

5 How Much Control to Hand the Model

The control loop carries a design decision the other components inherit: how much of the trajectory the runtime fixes and how much the model decides. Practitioner guidance draws the line between a workflow, defined as a system “where LLMs and tools are orchestrated through predefined code paths,” and an agent, defined as a system “where LLMs dynamically direct their own processes and tool usage” (Schluntz and Zhang 2024). The same guidance recommends the simplest structure that solves the task and adds autonomy only when a fixed path cannot be specified in advance (Schluntz and Zhang 2024). This is a recommendation drawn from deployment experience rather than a benchmarked result, but it names the axis the loop is built on: predictability against flexibility.

6 What This Series Covers

The six responsibilities are the survey’s decomposition. For exposition, this series groups them into four families and adds one further topic; the grouping is a convenience of presentation, not a claim that four families are more correct than six responsibilities, and the mapping is stated so the coarser labels trace back.

  • The Loop treats the control loop \mathcal{L}: the reason-act-observe cycle, planning, reflection, search over trajectories, and the workflow-versus-agent choice above.
  • Tools and Interfaces treats the action interface \mathcal{I}_{\mathrm{act}} together with the observation interface \mathcal{I}_{\mathrm{obs}}: how commands, schemas, and feedback formats shape the agent’s effective action space, with the ACI as the reference case.
  • Context treats the context manager \mathcal{C} and the state and artifact store \mathcal{S}: what enters each call, how memory is compressed and retrieved, and how state persists across a long run.
  • Evaluation treats verification and governance \mathcal{V}: tests, judges, and the benchmarks that measure whether a harness works.

A closing post treats self-improvement, where the harness itself becomes a learnable object and, in the survey’s fourth paradigm, the model, harness, and improvement loop co-evolve from execution traces (Guo et al. 2026; Gao et al. 2025).
