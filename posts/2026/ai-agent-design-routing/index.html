1 Problem Setup

Modern agent systems are often described through an oversimplified abstraction. A common formulation assumes that one provides a model with a prompt, exposes a set of tools, and allows the model to act. While this description is sufficient for small-scale demonstrations, it becomes inadequate once the system supports delegation, background execution, isolated environments, or long-running tasks.

In such settings, the primary challenge is no longer prompt design. The central problem becomes routing.

Routing refers to the layer that determines the computational interpretation of a request. Given a high-level instruction, the system must decide where the work executes, how it is scheduled, how it is tracked, and which runtime object represents it. The purpose of this discussion is to formalize this layer as a mapping from model intent to an explicit task contract.

2 From Prompting to Systems Design

Consider a coordinator agent that produces high-level instructions such as parallel research, isolated implementation, continuation of an existing worker, or background verification. These outputs reflect meaningful decisions at the level of intent.

However, these decisions are not yet executable. A concrete system must still resolve execution semantics, including whether the work runs in the foreground or background, whether execution occurs locally or remotely, whether a new worker is instantiated or an existing one is resumed, and how lifecycle events such as cancellation or monitoring are handled.

This motivates a strict separation between intent and execution semantics. The model specifies what should be done, while the runtime determines how it is realized. Maintaining this boundary is a key principle in stable agent architectures.

3 Three-Layer Architecture

A structured design separates the system into three layers: the policy layer, the routing layer, and the task contract layer. Each layer corresponds to a distinct abstraction boundary.

3.1 Policy Layer

The policy layer defines the decision surface of the model. It specifies the coordinator role, the available tools, the capabilities of workers, and the general orchestration rules. This layer shapes behavior indirectly by influencing the distribution over actions.

Formally, one may view the policy as a mapping \pi_\theta(a \mid s), where s encodes the current context and a represents a high-level delegation action.

The policy layer should remain lightweight. Its purpose is to guide decision-making rather than instantiate runtime objects.

3.2 Routing Layer

The routing layer transforms high-level actions into execution paths. Given a delegation request, the router selects a task kind based on constraints such as isolation requirements or execution mode.

This can be formalized as a deterministic mapping k = f_{\text{route}}(r), where r denotes the request and k denotes the selected execution type.

At this stage, abstract intent is converted into a concrete execution structure.

3.3 Task Contract Layer

Once a route is selected, the system constructs a task contract. This object represents the work explicitly and defines its lifecycle, identity, status, and outputs.

The task contract ensures that execution is observable and controllable. It provides a structured interface for monitoring progress, handling cancellation, and managing persistence.

4 Why Policy Should Not Create Tasks

A common design error is to allow the policy layer to instantiate tasks directly. This blurs the boundary between soft decision logic and hard execution semantics.

The distinction matters because prompt-based logic is inherently unstable. It changes as role descriptions, tool definitions, and orchestration heuristics are revised. Execution semantics, by contrast, should remain deterministic. Decisions such as whether work runs in the background, whether isolation is required, how lifecycle transitions are handled, and how outputs are persisted must be governed by code rather than prompt wording.

Once these concerns are mixed, both layers become harder to maintain. Small prompt edits can unintentionally alter runtime behavior, while execution rules become difficult to reason about and enforce. For this reason, policy should shape routing decisions, but it should not replace routing logic.

This separation also clarifies the role of the agent builder. In practice, the builder is not merely a construction utility. It validates requests, resolves constraints, selects execution modes, assembles runtime parameters, and creates task contracts. Architecturally, it is best understood as a combination of a router and a factory, operating at the boundary between model-generated intent and system-level execution.

5 Task Contracts

The task contract is a central abstraction in multi-agent systems. Without it, execution remains implicit and difficult to control. With it, work becomes a first-class object that can be inspected, stored, and managed.

A well-defined task contract answers several questions: the type of the task, its current state, its output location, and whether it can be resumed or terminated. This explicit representation distinguishes robust runtimes from ad hoc orchestration systems.

The following example illustrates a minimal contract structure.

from dataclasses import dataclass, field
from enum import Enum
from typing import Optional
import time
import uuid


class TaskStatus(str, Enum):
    PENDING = "pending"
    RUNNING = "running"
    COMPLETED = "completed"
    FAILED = "failed"
    KILLED = "killed"


class TaskKind(str, Enum):
    LOCAL_FOREGROUND = "local_foreground"
    LOCAL_BACKGROUND = "local_background"
    REMOTE = "remote"
    TEAMMATE = "teammate"


@dataclass
class Task:
    id: str
    kind: TaskKind
    status: TaskStatus
    description: str
    prompt: str
    output_path: str
    start_time: float
    end_time: Optional[float] = None
    notified: bool = False


def create_task(kind: TaskKind, description: str, prompt: str) -> Task:
    task_id = str(uuid.uuid4())
    return Task(
        id=task_id,
        kind=kind,
        status=TaskStatus.PENDING,
        description=description,
        prompt=prompt,
        output_path=f"/tmp/tasks/{task_id}.log",
        start_time=time.time(),
    )

Although the exact fields may vary, the key idea is that execution is represented explicitly rather than embedded in prompt flow.

6 Design Patterns

The architecture can be understood as a composition of several classical software design patterns. The strategy pattern governs the selection of execution modes, where different task kinds correspond to different execution strategies. The factory pattern centralizes task creation, ensuring consistent construction of runtime objects. The builder pattern appears in the incremental assembly of execution parameters, including worker type, prompt, and permissions. The state machine pattern captures lifecycle transitions such as pending, running, and completed states. Finally, the registry pattern provides persistent storage and indexing for tasks. Together, these patterns create a coherent and extensible runtime structure.

The following skeleton makes the separation of responsibilities explicit.

6.1 Routing

from dataclasses import dataclass
from typing import Optional


@dataclass
class DelegationRequest:
    description: str
    prompt: str
    team_name: Optional[str] = None
    worker_name: Optional[str] = None
    isolation: str = "local"
    run_in_background: bool = False


class TaskRouter:
    def route(self, request: DelegationRequest) -> TaskKind:
        if request.team_name and request.worker_name:
            return TaskKind.TEAMMATE

        if request.isolation == "remote":
            return TaskKind.REMOTE

        if request.run_in_background:
            return TaskKind.LOCAL_BACKGROUND

        return TaskKind.LOCAL_FOREGROUND

6.2 Factory

class TaskFactory:
    def create(self, request: DelegationRequest) -> Task:
        kind = TaskRouter().route(request)
        return create_task(
            kind=kind,
            description=request.description,
            prompt=request.prompt,
        )

6.3 Registry

class TaskRegistry:
    def __init__(self) -> None:
        self._tasks: dict[str, Task] = {}

    def add(self, task: Task) -> None:
        self._tasks[task.id] = task

    def get(self, task_id: str) -> Optional[Task]:
        return self._tasks.get(task_id)

    def update_status(self, task_id: str, status: TaskStatus) -> None:
        task = self._tasks[task_id]
        task.status = status
        if status in {TaskStatus.COMPLETED, TaskStatus.FAILED, TaskStatus.KILLED}:
            task.end_time = time.time()

    def all(self) -> list[Task]:
        return list(self._tasks.values())

6.4 Runner

class TaskRunner:
    def run(self, task: Task) -> None:
        task.status = TaskStatus.RUNNING

        try:
            if task.kind == TaskKind.REMOTE:
                self._run_remote(task)
            elif task.kind == TaskKind.TEAMMATE:
                self._run_teammate(task)
            elif task.kind == TaskKind.LOCAL_BACKGROUND:
                self._run_background(task)
            else:
                self._run_foreground(task)

            task.status = TaskStatus.COMPLETED
            task.end_time = time.time()
        except Exception:
            task.status = TaskStatus.FAILED
            task.end_time = time.time()

6.5 Runtime

class AgentRuntime:
    def __init__(self) -> None:
        self.factory = TaskFactory()
        self.registry = TaskRegistry()
        self.runner = TaskRunner()

    def delegate(self, request: DelegationRequest) -> Task:
        task = self.factory.create(request)
        self.registry.add(task)
        self.runner.run(task)
        return task

This structure enforces a clear decomposition. The policy layer governs intent. The routing layer selects execution. The factory constructs the task contract. The registry maintains state. The runner executes the task.

Many system failures arise from architectural issues rather than model limitations. If the model directly controls execution semantics, the system becomes inconsistent because prompts do not provide stable guarantees. If background work is not represented explicitly, the system loses observability and control. If routing logic is distributed across components, behavior becomes fragmented. If policy and runtime are tightly coupled, small prompt changes can produce unintended execution differences. These failure modes are avoided by maintaining strict abstraction boundaries.

A concise summary of the architecture is given by the following principle.

Let the model choose intent. Let code choose execution semantics.

This separation ensures that reasoning and execution remain independently evolvable. The policy can improve decision quality, while the runtime preserves consistency and reliability. The central problem in agent systems is not merely how to expose tools to a model. A more fundamental problem is how to transform a high-level decision into a reliable runtime object. Routing serves as this transformation layer. It connects model intent to execution reality. In any non-trivial coordinator-worker system, this layer is not auxiliary infrastructure. It is the core of the agent builder.
