Holding the language model fixed and changing only the interface through which it reads and edits code moves task performance by a wide margin. On the 300-instance SWE-bench Lite split, SWE-agent with GPT-4 Turbo resolves 18.0% of issues with its full interface, 10.3% when the file editor is removed, and 15.0% when only the edit-time syntax checker is removed (Yang et al. 2024). The weights are identical across these runs. What changes is the set of commands the model can issue and the format of the feedback it receives.

The harness-design survey names two of the six runtime responsibilities of a harness as the action interface \mathcal{I}_{\mathrm{act}}, which maps model outputs to executable operations and defines what the agent can do, and the observation interface \mathcal{I}_{\mathrm{obs}}, which determines which environment signals are exposed and how they are rendered (Guo et al. 2026). Together they fix what an agent can do and what it can see. This post treats their design: the commands and schemas an agent invokes, the way results and errors are formatted, the standardization of that surface across systems, and the benchmarks that measure whether a given interface works. It does not treat the control loop that decides which action to take, or context management beyond the interface, except where the interface determines them.

1 An Agent Is a New Class of Interface User

SWE-agent introduces the agent-computer interface (ACI), an abstraction layer between the model and the computer that fixes both the commands available to the model and how the environment state is communicated back to it (Yang et al. 2024). The paper argues that language-model agents are a new category of end user, distinct from the two users existing interfaces were built for: application programming interfaces target other software, and graphical user interfaces target humans. A shell configured for a human, or an API designed for a program, is not the interface that serves a language model best.

The argument rests on concrete differences in ability. The paper notes that current models lack the visual understanding to operate graphical applications directly, so features such as syntax checking and navigation must be surfaced as text if the agent is to use them (Yang et al. 2024). It also notes that a human can flexibly ignore irrelevant content, whereas for a model all content carries a fixed cost in the context window and distracting content degrades performance. An interface built for a human therefore mismatches the agent on exactly the dimensions that determine agent success.

Working from a fixed model and tuning the interface on a development set, by manual inspection of agent behavior and a grid search over configurations, the paper states four design principles (Yang et al. 2024). Actions should be simple, with few options and concise documentation, so the agent can use them without demonstrations or fine-tuning. Actions should be compact and efficient, consolidating a high-level operation into a single command rather than requiring several to compose. Environment feedback should be informative but concise, reporting the effect of an action without extraneous detail. And guardrails, such as a syntax checker that rejects a malformed edit, should catch errors early to prevent them from propagating. The remaining sections read the empirical results through these four principles.

2 The Action Interface: Commands Built for a Model

SWE-agent replaces the general shell with a small set of purpose-built commands for the software-engineering task: find_file, search_file, and search_dir for navigation, open with scroll_up, scroll_down, and goto for viewing, and an edit command for modification (Yang et al. 2024). Each command embodies the design principles. The search commands return at most 50 results and, when a query exceeds that, report nothing and ask the agent to refine the query, which enforces concise feedback rather than flooding the context with matches. The edit command takes a start line, an end line, and replacement text, and applies a multi-line edit in a single step, which consolidates an operation that the raw shell would spread across several fragile sed or redirection commands.

The interface ablations isolate the contribution of each of these choices under a fixed model, SWE-agent with GPT-4 Turbo on SWE-bench Lite. The full configuration resolves 18.0% of instances; each row below replaces one component with an alternative and holds everything else constant (Yang et al. 2024).

Component Variant % Resolved
Editor edit with linting (full) 18.0
Editor edit without linting 15.0
Editor no edit command 10.3
Search summarized (full) 18.0
Search iterative 12.0
Search no search 15.7
File viewer 100-line window (full) 18.0
File viewer 30-line window 14.3
File viewer whole file 12.7

Removing the edit command and leaving the agent to modify files through shell redirection and sed is the single largest regression, from 18.0% to 10.3% (Yang et al. 2024). The paper attributes this to the absence of consolidated, feedback-bearing edits: redirection rewrites whole files for a small change, sed makes multi-line edits cumbersome, and neither reports what changed, so the model operates without immediate confirmation.

One row inverts the naive expectation that a more capable-looking tool helps. The iterative search interface, modeled directly on the human editor experience of stepping through matches with next and prev, resolves 12.0%, below the 15.7% of providing no search tool at all (Yang et al. 2024). The paper reports that, given many matches, agents step through every result exhaustively, exhausting the cost budget or context window. The summarized interface, which lists results at once and refuses over-broad queries, avoids this and reaches 18.0%. The failure is not of the model but of an interface transplanted from human use, which is the ACI premise stated as a measured result.

The same principle of consolidation and clear naming appears in practitioner guidance on tool design, framed for the general case of an agent calling arbitrary tools rather than editing code. The engineering account of writing tools for agents recommends consolidating functionality, replacing a set of narrow tools such as list_users, list_events, and create_event with a single higher-level schedule_event, and namespacing tools by service and resource, for example asana_search and jira_search, so the agent can select the right one (Aizawa 2025). It reports that even small refinements to tool descriptions can improve outcomes, and that Claude Sonnet 3.5 reached state-of-the-art performance on SWE-bench Verified after such refinements. This is a report from deployment rather than a controlled ablation, and it is stated as such here, but it names the same lever the SWE-agent ablations quantify: the specification of the action, not the capability of the model.

At the level of general APIs rather than shell commands, ToolLLM shows one concrete encoding of the action interface (Qin et al. 2023). Each API is presented to the model as a callable function, with its documentation placed in the model’s function field, and two terminal functions are added to the action space, “Finish with Final Answer” and “Finish by Giving Up”, the latter letting the agent abandon a task whose tools cannot solve it. At each step the model emits a thought, an API name, and its parameters, and receives the real API response. The action interface here is the function schema and the two control actions, defined so that both success and principled failure are expressible.

3 The Observation Interface: Feedback as Part of the Interface

The feedback an interface returns is a design object with the same weight as the commands it accepts. SWE-agent integrates the file viewer with the editor so that after an edit the viewer automatically redisplays the updated lines, letting the agent observe the effect of its change without issuing a further command (Yang et al. 2024). When a command produces no output, the interface substitutes an explicit message that the command ran successfully and produced none, rather than returning an empty observation the model must interpret.

The file-viewer ablation shows that the observation interface has an interior optimum rather than a monotone preference for more information. Both a 30-line window (14.3%) and displaying the whole file (12.7%) resolve fewer instances than the 100-line window (18.0%) (Yang et al. 2024). Too little context forces repeated scrolling; too much fills the context window with lines that do not bear on the edit. The informative-but-concise principle is a balance point, not a direction.

The clearest case for feedback as a guardrail is the edit-time syntax checker. SWE-agent integrates a linter into the edit command: an edit is applied only if it does not introduce major errors, and an invalid edit is discarded with a message asking the agent to try again (Yang et al. 2024). Removing only the linter, and keeping the consolidated edit command, drops performance from 18.0% to 15.0%. The trajectory analysis explains why the effect is this large. Out of 2294 instances, 1185 (51.7%) of the GPT-4 Turbo trajectories contain at least one failed edit, and although any edit attempt eventually succeeds with probability 90.5%, that probability falls to 57.2% after a single failed edit. Errors compound, and feedback that catches a malformed edit at the moment it is made interrupts the compounding.

Practitioner guidance quantifies the token cost that the fixed-cost observation raises. The account of writing tools for agents reports that Claude Code restricts tool responses to 25,000 tokens by default and recommends pagination, range selection, filtering, and truncation with sensible defaults when a response would exceed that (Aizawa 2025). It also proposes letting the agent choose response verbosity through a format parameter, reporting an example in which a concise response used roughly one third the tokens of the detailed one, 72 against 206, while preserving the information the agent needed. These are production defaults rather than benchmarked results, but they operationalize the same observation SWE-agent makes: because every returned token has a fixed cost for the model, the volume and format of feedback are part of the interface, not an afterthought.

4 From Calling Tools to Designing the Tool Surface

Two questions run through the tool-use literature and are easy to conflate. One is whether a model can call a tool at all: whether it emits a syntactically valid call at the right moment. The other is how the tool surface is presented: what documentation, schema, and feedback the model reads when it does. The interface question is the second, and the lineage from Toolformer to Gorilla to ToolLLM moves the emphasis from the first to the second.

Toolformer addresses whether and when to call a tool, and solves it without supervision of where a tool would help (Schick et al. 2023). The model samples candidate API calls at positions in ordinary text, executes them, and keeps a call only if its result lowers the model’s loss on the tokens that follow. For a candidate call c_i with result r_i at position i, writing \mathbf{e}(c_i, r_i) for the call-and-result rendered as a prefix and \varepsilon for the empty prefix, the paper defines

L_i^{+} = L_i\big(\mathbf{e}(c_i, r_i)\big), \qquad L_i^{-} = \min\big(L_i(\varepsilon),\, L_i(\mathbf{e}(c_i, \varepsilon))\big),

and retains the call when L_i^{-} - L_i^{+} \ge \tau_f for a threshold \tau_f. Why this form? There is no labeled corpus of where a tool is useful, so the model’s own next-token loss stands in as the utility signal, and a call is kept only when seeing its result makes the continuation more predictable. The minimum in L_i^{-} is what makes the test demand that the result carry the benefit: the comparison baseline is the better of making no call and making the call but discarding its result, so a call that helps only by cueing the model’s phrasing, without its returned value mattering, does not pass. Trained this way, a 6.7B-parameter GPT-J model using a calculator, a question-answering system, a Wikipedia search, a translation system, and a calendar outperforms the far larger GPT-3 175B on the mathematical and factual benchmarks where the tool supplies the missing computation or fact (Schick et al. 2023).

Toolformer’s stated limitations mark exactly where the interface question begins. The paper notes that its API calls are generated independently, so the model cannot chain tools by feeding one tool’s output into another, and cannot use a tool interactively, for example by browsing search results and refining a query (Schick et al. 2023). These are properties of the interface and the loop, not of whether the model can emit a call.

Gorilla moves the emphasis to how API documentation enters the interface and makes the failure mode of a misused interface a measured quantity (Patil et al. 2023). It defines a hallucination precisely, as an API call that is not a subtree of any API in the reference database, that is, an invented tool, and separates it from an error, a real API invoked incorrectly, scoring both by abstract-syntax-tree subtree matching against APIBench, a dataset of 1645 model-hub APIs drawn from TorchHub, TensorHub, and HuggingFace. Its interface mechanism is retrieval-aware training: the relevant API document is concatenated into the prompt behind a fixed instruction to use it for reference, both during training and at inference, so the model learns to read current documentation and can adapt when a document changes at test time. The paper reports that the fine-tuned LLaMA-7B model, evaluated zero-shot, writes API calls more accurately than GPT-4 while sharply reducing hallucinated calls (Patil et al. 2023). It also reports that retrieval does not always help: a weak retriever supplying the wrong document can lower accuracy below the no-retrieval setting, so the benefit is contingent on retrieval quality rather than automatic.

ToolLLM addresses the scale at which the tool surface no longer fits in a prompt (Qin et al. 2023). Its ToolBench dataset covers 16,464 real REST APIs, bundled into 3,451 tools across 49 categories from RapidAPI Hub. At that scale the action interface cannot be a fixed list of tools, so the system trains a neural API retriever that selects a small relevant subset for each instruction, and the model plans over that subset. Retrieving the tools is itself an interface decision: the paper reports that feeding the model a retrieved subset can outperform giving it a hand-picked set, because the retriever surfaces relevant substitute APIs the annotator did not choose. The progression across the three papers is from establishing that a model can call tools, to presenting documentation and controlling hallucination, to selecting and scaling the tool surface, and only the first is a question about the model in isolation.

5 Standardizing the Interface: The Model Context Protocol

The interfaces above are each defined per system. The Model Context Protocol (MCP) is an open protocol that standardizes how an application supplies tools and context to a language model, using JSON-RPC 2.0 messages and capability negotiation between a host, its clients, and servers, with the message types defined by a published schema (Model Context Protocol 2025). Its relevance here is the distinction it draws among three server-provided primitives. A server exposes tools, which are functions for the model to execute; resources, which are context and data for the user or the model to read; and prompts, which are templated messages and workflows for the user.

The reason to separate the three is that they differ in who controls invocation and in the risk they carry. The specification frames tools as model-invoked actions, while resources and prompts are supplied under application and user control, and it treats a tool as arbitrary code execution: it states that a host must obtain explicit user consent before invoking any tool, and that tool descriptions must be considered untrusted unless they come from a trusted server (Model Context Protocol 2025). Read against the action-and-observation decomposition, MCP standardizes the boundary the earlier systems each drew by hand, and it draws the same line the SWE-agent design draws between what the agent may do and what it may read, now as a protocol-level distinction with consent attached to the acting side.

6 Measuring Whether the Interface Works

An interface claim is only as good as the evaluation that isolates it, and the benchmarks for tool use measure progressively harder properties. The Berkeley Function-Calling Leaderboard evaluates single-turn function-calling: whether a model, given a set of function schemas and a request, emits the correct call on real-world APIs (UC Berkeley Gorilla Team 2024). It measures the narrow interface question of call correctness in isolation from multi-turn interaction.

\tau-bench raises the bar to a multi-turn setting in which the agent interacts both with domain API tools and with a language-model-simulated user, under written policy guidelines, across a retail domain of 115 tasks and an airline domain of 50 tasks (Yao et al. 2024). Its evaluation avoids human judgment by comparing the database state at the end of the conversation against a unique annotated goal state. The reward of an episode is a product,

r = r_{\mathrm{action}} \cdot r_{\mathrm{output}} \in \{0, 1\},

where r_{\mathrm{action}} is one only if the final database matches the ground-truth outcome and r_{\mathrm{output}} is one only if the agent’s replies conveyed the required information to the user. The product form encodes that a task is complete only when both hold: an agent that reaches the correct world state but never tells the user the needed fact, or that says the right thing while leaving the database wrong, scores zero. To measure reliability rather than best-case success, the paper defines, for a task run n times with c successes,

\mathrm{pass}^{k} = \mathbb{E}_{\mathrm{task}}\!\left[\frac{\binom{c}{k}}{\binom{n}{k}}\right],

the probability that all k independent trials of a task succeed. This inverts the emphasis of \mathrm{pass}@k, which is one minus the probability that all k trials fail and so rewards discovering a solution in at least one of several attempts. The paper’s stated motivation is that a deployed agent must handle semantically equivalent conversations consistently, so the relevant quantity is the chance every trial succeeds, not the chance one does (Yao et al. 2024). Measured this way, the best function-calling agent tested, gpt-4o, reaches a \mathrm{pass}^1 of 48.2% on average, 61.2% in retail and 35.2% in airline, and its reliability falls to below 25% at \mathrm{pass}^8 in retail. The paper attributes the gap to insufficient consistency and rule-following. An ablation that removes the policy document from the prompt supports this: it barely changes retail performance but sharply lowers airline performance, indicating that in the easier domain the agent was often not leveraging the policy at all.

\tau^2-bench extends the evaluation to a property the earlier benchmarks cannot express: coordination with another actor who also holds tools (Barres et al. 2025). Where \tau-bench is single-control, meaning only the agent acts on the world and the simulated user only supplies information, \tau^2-bench introduces a dual-control Telecom domain in which the simulated user also has tools to observe and change a shared environment. It models the setting as a decentralized partially observable Markov decision process, with the agent and the user as two decision-makers over separate observations of one state, and generates 114 sampled tasks from a combinatorial space of 2285 built by composing atomic subtasks. The headline result isolates the cost of coordination: moving from a solo setting, in which one agent controls all tools including the user’s, to the dual-control setting drops \mathrm{pass}^1 by 18% for GPT-4.1 and 25% for o4-mini, with GPT-4.1 reaching 34% and Claude 3.7 Sonnet 49% on the Telecom tasks. Because the solo setting removes only the need to guide another actor while holding the reasoning and tool-calling load fixed, the gap between the two attributes failure specifically to communication and decentralized control rather than to reasoning. This is the verification responsibility of the harness applied to the interface, and it shows the measured object moving from call correctness, to multi-turn reliability, to coordination through the interface with a second party.

The evidence across these sources supports a single reading. Under a fixed model, the interface through which an agent acts and observes is a distinct performance lever, and the SWE-agent ablations quantify it directly: the file editor is worth 7.7 points on SWE-bench Lite, the edit-time linter 3.0, and an interface borrowed from human use can underperform no tool at all. The four design principles, simple actions, compact actions, informative-but-concise feedback, and guardrails, recur from the shell commands of SWE-agent to the general tool-design guidance and the function schemas of ToolLLM. The tool-use lineage separates the model’s capacity to call a tool from the design of the tool surface, MCP standardizes the boundary between acting and reading that the individual systems each drew by hand, and the \tau-bench family measures whether a given interface yields not just occasional success but reliable, policy-compliant, and coordinated behavior.

The next post in the series turns from the interface to what passes through it over a long run: the context manager and the state store, which select and compress what enters each model call and persist progress beyond the active context window.
