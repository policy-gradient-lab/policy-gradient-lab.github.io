Every agent runs a loop: the model reads the state of its environment, decides on an action, executes it, reads the result, and repeats until the task is complete or abandoned. How that loop is structured, what the agent does next, when it halts, and how it recovers from a failed step, is the control-flow layer of the harness. This layer is sometimes called loop engineering; the established terms are agent architecture and control flow.

Across the methods that populate this layer, one variable separates them more than any other: how much of the decision about what to do next is left to the model at run time, and how much is fixed in code before the run begins. A single ReAct step hands the model near-total latitude to pick its next action. A statically compiled execution graph fixes the sequence in advance and lets the model fill only the leaf nodes. The methods below are ordered along that axis, from maximal delegation to its withdrawal, because the ordering is also roughly the field’s chronology and makes the design trade-offs legible.

The scope is deliberately narrow. This post covers single-agent control flow: the loop, its reflective and planning extensions, search over loops, and the recent move to lift control flow out of the model’s context. It does not treat the harness’s other layers, namely tool and interface design, context management, and evaluation, each of which is a separate post in this series. Multi-agent orchestration appears only where a single-agent pattern generalizes to it.

1 The Minimal Loop: Observe, Reason, Act

The smallest useful control loop alternates three operations: the model emits a reasoning trace, emits an action, and reads back an observation from the environment, then repeats. ReAct introduced this interleaving of reasoning traces and task-specific actions in one decoding sequence (Yao, Zhao, et al. 2023). Before it, the two were separate: chain-of-thought produced reasoning with no way to consult the world, and action-only agents acted with no explicit reasoning between steps.

Interleaving addresses a specific failure of each. A reasoning-only trace has no external check, so a hallucinated fact is carried forward without correction; the paper reports that hallucination is a serious problem for chain-of-thought, producing a higher false-positive rate than ReAct, which it finds more factual and grounded (Yao, Zhao, et al. 2023). An action-only agent has no place to record why it chose an action, so it cannot decompose a goal or track progress across steps. Interleaving lets each observation ground the next thought and each thought condition the next action.

2 Reflection: Turning a Failed Trajectory Into the Next Prompt

The ReAct loop improves within a single trajectory but retains nothing across attempts. Reflexion adds an outer loop that does. After a trial ends, an evaluator scores the trajectory, a language model converts the trajectory and its score into a natural-language summary of what went wrong and what to change, and that summary is written to a memory buffer and added to the agent’s context on the next attempt (Shinn et al. 2023). The model is never fine-tuned; the only thing that changes between attempts is the text in its context.

The paper states this by redefining the policy that reinforcement learning would optimize. In place of a weight vector \theta, it writes

\theta = \{M_a,\ \mathit{mem}\},

where M_a is the fixed action-generating model and \mathit{mem} is the accumulated reflection text (Shinn et al. 2023). Why locate the optimization in \mathit{mem} rather than in the model’s weights? A gradient update spreads a scalar reward across the parameters through credit assignment the optimizer performs opaquely. An update to \mathit{mem} is an explicit, human-readable string appended to a buffer, and the feedback it carries can be far more specific than a scalar. The cost is that improvement is bounded by what the model can extract from its own context and act on, with no convergence guarantee. On this loop the paper reports absolute gains of 22% on AlfWorld decision-making, 20% on HotPotQA reasoning, and 11% on HumanEval code generation, reaching 91% pass@1 on HumanEval (Shinn et al. 2023).

In control-flow terms the delegation is still high but no longer uniform across time. The reflection step is a fixed piece of scaffolding, run on a fixed schedule after each trial, that shapes what the model sees on the next iteration. LangChain’s reflection-agent tutorial makes the schedule concrete as a two-node graph, a generator and a reflector, that alternate for a fixed number of rounds before returning. The loop structure is fixed in code; the content the model produces inside it is not.

3 Planning: Commit Up Front or Revise on the Fly

Reflection changes the prompt between attempts but leaves the within-attempt structure to the model step by step. Planning methods instead fix some of that structure before acting, and they differ in how firmly.

Plan-and-Solve prompting is the open-loop case. A single prompt instructs the model first to devise a plan that divides the task into subtasks and then to carry out the subtasks in order, all in one pass (Wang et al. 2023). The plan is generated once and not revised against execution feedback. The paper’s target is a specific failure of zero-shot chain-of-thought, missing-step errors, and the extended variant PS+ adds more detailed instructions to reduce calculation errors. The control content here is a plan the model commits to at the start, which removes some step-by-step latitude but provides no mechanism to change the plan when a step fails.

The closed-loop case reintroduces revision. LangChain’s plan-and-execute pattern separates a planner that produces the full task breakdown, an executor that works through each subtask, and a re-planner that is invoked when execution diverges from the plan and rewrites the remaining steps. Control alternates between a fixed structure, the current plan, and the model, which both executes steps and, through the re-planner, proposes edits to the structure. This returns to the model some of the authority that the open-loop plan withdrew, but only at the re-planning boundary rather than at every step.

ADaPT calibrates the same choice to the executor’s observed capability (Prasad et al. 2023). It attempts a task directly, and only when the executing model fails to complete a subtask does it recursively decompose that subtask into smaller ones, stopping the recursion where the model can already execute. Decomposition is spent where it is needed and withheld where it is not, so the depth of the fixed plan structure adapts to both task complexity and model ability rather than being set uniformly in advance. The paper reports success rates up to 28.3% higher on ALFWorld, 27% higher on WebShop, and 33% higher on TextCraft than the baselines it compares against (Prasad et al. 2023).

4 Searching Over Loops: Trees and Rollouts

The methods above run one trajectory at a time. A further step keeps several partial trajectories alive at once and applies an explicit search procedure to choose among them, which moves the control decision out of the model and into the search operator.

Tree of Thoughts generalizes a linear reasoning chain to a tree whose nodes are intermediate steps, called thoughts, that can be expanded, evaluated, and abandoned (Yao, Yu, et al. 2023). The model proposes candidate next thoughts and also scores states through a value or voting prompt; a search algorithm, breadth-first or depth-first, decides which nodes to expand and which to prune. The value of separating proposal from search shows on tasks where a single forward pass is unreliable. On Game of 24, GPT-4 with chain-of-thought prompting solves 4% of instances and standard few-shot prompting 7%, while Tree of Thoughts solves 74% (Yao, Yu, et al. 2023). The gain comes from backtracking: a wrong early step can be discarded and a sibling explored, which a single linear trajectory cannot do.

LATS synergizes reasoning, acting, and planning in one framework by expanding ReAct into a search over possible reasoning and acting steps with Monte Carlo Tree Search (Zhou et al. 2023). Nodes are states in a ReAct-style trajectory, the model supplies both an action proposer and a value function that scores states by expected future reward, and failed rollouts generate Reflexion-style summaries that feed back into later expansions. The selection step, which decides where in the tree to expand next, uses a variant of the UCT rule:

a_t \;=\; \arg\max_{a \in e(s_t)} \left[\, V(s_t) \;+\; w \sqrt{\frac{\ln N(s_t)}{N(s_{t+1})}} \,\right].

The first term V(s_t) is the value the model assigns to the state, so it favors branches that look good so far, the exploitation component. The second term grows when the parent has been visited many times, through \ln N(s_t), but the child few, through N(s_{t+1}) in the denominator, so it favors under-explored branches, the exploration component; the weight w trades the two off. Why this form rather than picking the highest-valued child outright? A pure-value rule would commit to whichever branch the model’s value function scored highest early and never test the alternatives, and the value function is itself an unreliable model estimate. The logarithmic-over-count exploration term forces the search to sample less-visited branches enough to correct early misjudgments, which is the property greedy selection lacks. With this procedure LATS reports 92.7% pass@1 on HumanEval with GPT-4, and an average score of 75.9 on WebShop with GPT-3.5, the latter without any gradient updates (Zhou et al. 2023).

At this point on the axis the model no longer decides what to do next. It proposes and it scores; an explicit algorithm outside it decides which proposal to pursue. The gain in reliability is bought with many more model calls per solved instance, since the search expands and evaluates many nodes that the final trajectory does not use.

5 How Much of the Loop Should the Model Run?

The methods so far each pick a point on the delegation axis. A practitioner account from Anthropic argues that the point should be chosen per task and defaulted low. It draws a line between workflows, in which language models and tools are orchestrated through predefined code paths, and agents, in which the model dynamically directs its own process and tool use (Schluntz and Zhang 2024). The two are the low and high ends of the same axis this post has been tracing.

The account catalogs five composable patterns and presents them roughly in order of increasing delegation: prompt chaining, which fixes a sequence of model calls; routing, which classifies an input and dispatches it to a specialized follow-up; parallelization, which runs independent calls concurrently and aggregates them; orchestrator-workers, in which a model decomposes a task and dispatches subtasks to worker calls; and evaluator-optimizer, in which one call generates and another critiques in a loop (Schluntz and Zhang 2024). The first three fix the control flow in code and use the model only to fill steps; the last two hand the model a decision about what work to spawn or when to stop.

The account’s stated default is to prefer the simplest structure that works, and to add the dynamic decision-making of an agent only when a fixed workflow cannot handle the task’s variability (Schluntz and Zhang 2024). This is a design rule about where to sit on the axis, not a new mechanism: delegation to the model is a cost to be paid when needed, not a default to be assumed.

6 Production: Lifting Control Flow Out of the Context

The single-model loop remains the most common structure in deployed systems. A scheduler-theoretic study of 70 open-source LLM agent projects finds that 60%, 42 of the 70, adopt the Agent Loop, in which one model decides the next action by reading an ever-growing context window (Wei 2026). The study characterizes three structural weaknesses of that arrangement: dependencies between steps are implicit in the context rather than declared, recovery can loop without bound, and the execution history is mutable, which complicates debugging.

Its proposal, the Structured Graph Harness, withdraws the control decision from the model and encodes it as an explicit static directed acyclic graph (Wei 2026). Three commitments define it: an execution plan is immutable within a plan version, planning, execution, and recovery are separated into three distinct layers rather than interleaved in one loop, and recovery follows a fixed escalation protocol rather than free-form retry. The model fills the graph’s nodes; the graph, not the model, determines order, dependency, and recovery. This is the far end of the axis, where run-time delegation is reduced to node-local generation and the control flow is fixed before the run.

The frameworks in general use span the axis this describes. LangGraph models an agent as a graph of steps with explicit branching and retries; the OpenAI Agents SDK and the Claude Agent SDK provide loop implementations at a higher level, the latter being the runtime behind Claude Code. Where a system sits between a bare loop and a compiled graph is the control-flow decision this post has traced.

7 Putting It Together

The control layer of a harness is organized by a single choice: how much of the decision about what to do next is left to the model at run time. ReAct delegates that decision in full at every step. Reflexion keeps the per-step delegation but fixes an outer reflection step that rewrites the next prompt. Planning methods fix a plan before acting and differ in whether and when they revise it, with ADaPT tying the depth of that fixed structure to the model’s observed capability. Tree search removes the decision from the model entirely, letting it propose and score while an explicit operator chooses. The practitioner guidance is to treat delegation as a cost and default to the least of it that solves the task, and the structured-graph proposal takes that withdrawal to its limit by compiling the control flow into an immutable graph.

The next post in the series turns to the layer this one held fixed: the tools and interface through which the model’s chosen action reaches the environment, and why the design of that interface moves task performance as much as the loop that surrounds it.
